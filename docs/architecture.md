# Архитектура Deduplicator

Документ описывает устройство приложения: из каких проектов оно состоит, как идёт сканирование
и какие механизмы защищают данные пользователя.

## Проекты и зависимости

```
Deduplicator.App  ──►  Deduplicator.Core  ──►  FastDedup.Engine
                                                     ▲
FastDedup.Cli  ──────────────────────────────────────┘
Deduplicator.MftHelper  (отдельный процесс, запускается движком по требованию)
```

| Проект | Роль |
|---|---|
| `src/Deduplicator.App` | Avalonia UI (MVVM на CommunityToolkit.Mvvm), композиция сервисов, страницы и диалоги |
| `src/Deduplicator.Core` | прикладное ядро: сканирование, хэши, группировка, SQLite, файловые операции |
| `src/FastDedup.Engine` | низкоуровневые примитивы Windows: обход Win32/MFT/USN, идентичность файлов, детектор носителей |
| `src/Deduplicator.MftHelper` | узкий helper для чтения MFT; UI и база всегда работают без повышения прав |
| `src/FastDedup.Cli` | консольный запуск движка (`DedupOrchestrator`) |
| `tools/DedupBench` | воспроизводимый перф-харнесс: перечисление, воронка, пропускная способность хэша |

Главное окно работает с правами обычного пользователя (`asInvoker` в `src/Deduplicator.App/app.manifest`).
Для полного скана тома NTFS `ElevatedMftBroker` лениво запускает `Deduplicator.MftHelper`: UAC
показывается не больше одного раза за скан и только когда MFT-режим действительно применим.

## Пайплайн сканирования

1. **Перечисление.** `BackendSelector` выбирает бэкенд по цели:
   - целый том NTFS с доступным MFT-helper — `NtfsMft` (MFT/USN);
   - вложенная папка, exFAT/FAT32/ReFS, нет прав — `Win32Find`
     (`FindFirstFileExW` + `FIND_FIRST_EX_LARGE_FETCH`: размер и время приходят из `WIN32_FIND_DATA`,
     без отдельного `stat` на файл);
   - UNC/сеть — `Win32FindNetwork`.

   Если MFT недоступен (ошибка чтения, неподдерживаемая версия USN-записи, прогноз карты MFT
   больше 25 % доступной памяти по `MftMemoryPlanner`), обход прозрачно откатывается на Win32Find.
   При DOP > 1 `Win32FindMetadataEnumerator` разбирает очередь каталогов пулом воркеров.
2. **Метаданные.** `VolumeIndexer` применяет фильтры (мин. размер, расширения, скрытые/системные,
   системные папки), определяет категорию (`CategoryDetector`, в том числе по магическим байтам)
   и пишет записи батчами. Хэши переиспользуются только при точном совпадении size + mtime + created.
3. **Группировка по размеру.** Кандидаты читаются пачками размеров (`GetDuplicateSizeCandidates` +
   `GetBySizesOrdered`), короткоживущим reader-ом; между пачками выполняется пассивный чекпоинт WAL.
   Файлы с уникальным размером не читаются вовсе.
4. **Частичный хэш.** XxHash128 по голове и хвосту (64 КБ), размеру и, для файлов больше 128 МБ,
   среднему блоку (`partial_ver` = 2). Небольшие файлы на HDD читаются одним запросом.
5. **Полный хэш.** XxHash128 целиком, только для совпавших частичных хэшей, с двойной буферизацией.
   До и после чтения сверяется длина файла: изменившийся файл пропускается.
6. **Побайтовая сверка.** `DuplicateGrouper.ByteVerifyClusters` попарно сверяет подключённые файлы
   (на HDD блоками по 16 МБ). Ошибка чтения не считается равенством. Результат кэшируется в
   `verified_full_hash`, поэтому повторный скан того же носителя не перечитывает содержимое.
   Группы с офлайн- или непрочитанными членами получают `Confidence < 1.0` и не удаляются.
7. **Похожие файлы.**
   - Изображения: `ImagePerceptualPipeline` — продюсеры читают файлы по плану тома, ограниченный
     канал (около 128 МБ в полёте) передаёт данные декодерам, которые считают pHash и pixel-hash.
     Индекс — `PerceptualLsh` (8 полос по 8 бит), группировка потоковая. pHash байт-идентичных копий
     переносится по full_hash без повторного декода.
   - Аудио: отпечаток Chromaprint через внешний `fpcalc.exe` (таймаут 2 минуты на файл),
     сравнение по Жаккару на MinHash/LSH.
8. **Группы.** Точные и похожие группы привязаны к сессии скана (`duplicate_groups.scan_session_id`)
   и строятся только из файлов текущей области. Эталон выбирается `RepresentativeSelector`
   (правило «Умно» — `KeepScorer`). Точные результаты становятся видны прогрессивно, удаление
   доступно после завершения сессии.

Облачные плейсхолдеры (OneDrive «Файлы по запросу») не читаются ни на одном контентном этапе
(`CloudFiles`), чтобы офлайн-приложение не инициировало загрузку из облака.

## План чтения и губернатор ресурсов

- `VolumeReadPlan` строит план для каждого тома: HDD, медленные съёмные носители и сеть читаются
  последовательно, SSD/NVMe — параллельно. Тип носителя определяется по seek-penalty IOCTL (WMI —
  запасной путь). Разделы одного физического HDD делят одну последовательную очередь.
- `VolumeParallelExecutor` раздаёт статические квоты DOP по томам; общий потолок — сумма DOP томов,
  ограниченная удвоенным числом ядер (но не ниже DOP самого быстрого тома).
- `ResourceGovernor` пересчитывает бюджет конвейера на каждой странице перцептивного этапа:
  при высокой загрузке памяти канал сжимается до 32 МБ и число декодеров уменьшается.
  `ThroughputEwma` закрепляет устойчиво медленный носитель без seek-penalty (USB2, сеть) на одном
  потоке чтения.
- Режим «Эко» понижает приоритет процесса и читает в один поток.

## Прогресс

`ProgressCoalescer` схлопывает поток событий по файлам в редкие обновления UI (в `ScanService` интервал 200 мс, около 5 обновлений в секунду);
смена этапа и терминальные состояния отдаются сразу, устаревшие снимки отбрасываются по номеру
последовательности. `ScanProgressEstimator` считает общий процент, ETA и скорость.

## Инкрементальный скан и USN-дельта

- `volume_scan_state` хранит снимок USN-журнала тома после скана. `IncrementalScanPlanner`
  решает: полный пересбор, «без изменений» (перечисление пропускается) или инкремент.
- Инкремент: `UsnDeltaReader` читает записи `FSCTL_READ_USN_JOURNAL` от сохранённого водяного знака
  (не более 100 000 записей) и восстанавливает пути по FRN родителей. `UsnDeltaPlanner`
  классифицирует изменения, `UsnDeltaExecutor` переиндексирует только затронутые файлы.
- Любая аномалия (усечение журнала, запись версии не V2, каталожный rename/delete, путь вне тома,
  исчезнувший том, сбой посреди применения) приводит к безопасному полному пересбору тома.

## Переносимый индекс `.dedupindex`

`PortableIndexService` пишет скрытый файл `.dedupindex` в корень съёмного носителя. На другом
компьютере хэши берутся из него без перечитывания. Это только кэш: при расхождении серийного номера,
версий алгоритмов или метаданных файла он игнорируется, а побайтовая сверка и перепроверка перед
удалением им не обходятся.

## Безопасность данных

- **Атомарная запись** (`SafeIo.WriteAllTextAtomic`, `CopyAtomic`): временный файл с
  `FileOptions.WriteThrough`, сброс на диск, атомарное переименование.
- **Журнал до операции.** `FileOpsService` записывает намерение в `operations_log` до перемещения
  файла в Корзину или карантин; при неудаче перемещения запись откатывается. Не удалось записать
  журнал — файл не трогается.
- **Межтомовый перенос** (`SafeIo.MoveVerified`): копия → сверка хэша источника и копии → удаление
  источника. Если источник удалить нельзя, копия удаляется.
- **Карантин** — обратимое удаление с восстановлением через «Историю». Корзина недоступна
  (длинный путь, носитель без Корзины) — файл уходит в карантин.
- **Перепроверка перед удалением:** каждый файл заново проверяется на наличие и размер; изменённые
  или перемещённые блокируются. В группе всегда остаётся хотя бы одна доступная копия.
- **Замена жёсткими ссылками:** ссылка сначала создаётся под временным именем (`.dedup-hl`), затем
  атомарно замещает дубликат.
- **Групповое переименование** двухфазное (исходное → временное GUID-имя → финальное) с
  write-ahead журналом `RenameJournal` в `recovery\`.
- **Восстановление при старте** (`Composition`): удаление осиротевших `.dedup-tmp`/`.dedup-hl`,
  `RenameJournal.RecoverAll`, пометка незавершённых сессий как Failed и удаление их групп.
  Второй экземпляр приложения не запускается (именованный mutex).
- **Идентичность тома** (`VolumeIdentityGuard`): если носитель исчез или под той же буквой появился
  другой том, скан останавливается, чтобы не смешать данные разных носителей. Прунинг каталога
  тома не выполняется при ошибках перечисления.

## База данных

SQLite через `Microsoft.Data.Sqlite` (SQLitePCLRaw 3): `journal_mode = WAL`, `synchronous = NORMAL`,
`busy_timeout = 30000`, внешние ключи, запись транзакциями. Таблицы: `volumes`, `files`,
`duplicate_groups`, `duplicate_members`, `lsh_buckets`, `operations_log`, `scan_sessions`,
`volume_scan_state`, `scan_scope_sessions`, `scan_scope_files`, `scan_scope_volumes`,
`scan_pending_file_deletes`.

Перед миграцией схемы `Database` создаёт SQLite-backup (хранятся последние 3) и при ошибке
возвращает его на место. При инициализации `PRAGMA quick_check` выполняется до и после миграции. Публикация результатов скана
и отложенные удаления из индекса выполняются одной транзакцией.

## Объём каталога

Каталог хранит только метаданные и хэши, без содержимого файлов. Одна запись занимает примерно
0,4–0,7 КБ (путь, даты, хэши, индексы), аудио-отпечаток добавляет 0,5–2 КБ на трек:

| Файлов | Размер базы |
|---|---|
| 100 тыс. | ~50 МБ |
| 1 млн | ~0,5 ГБ |
| 10 млн | ~5 ГБ (+ аудио) |
